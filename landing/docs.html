overview

Cascade takes a trace of an ML workload captured on one real GPU and simulates it on other GPU configs, many copies at once. It has three parts.

  • Profiler. Runs your workload, for example a vLLM model, on a real GPU under Accel-Sim's NVBit tracer, and uploads the trace to Cascade while it is still tracing.
  • Cascade app. A Sail sandbox that receives traces, gets them ready to simulate, launches runs, and shows everything in a web UI.
  • Simulators. Each simulator is a fork of the app's sandbox, so it already has the trace on disk. It runs Accel-Sim 2.0 against one GPU config and reports progress back to the app.

The steps below take you from nothing to a finished run.

1. deploy the app

You need a Sail account and an API key. Pick any long random string as your Cascade token. The UI, the profiler and the simulators all use it.

git clone https://github.com/atoniolo76/cascade.git
cd cascade
export SAIL_API_KEY=...
export CASCADE_TOKEN=$(openssl rand -hex 24)
uv run --extra sail python scripts/deploy_sail.py \
  --base-image <simulator-image> \
  --sim-cmd "<simulator command>" \
  --accelsim-dir <path to accel-sim in that image>

The three flags point Cascade at the simulator image, the image with Accel-Sim and its trace post-processor built in. Without them, the app runs a stand-in simulator that replays a recorded Accel-Sim log, which is useful for trying the UI but doesn't simulate your trace.

The script creates the app's sandbox and prints two URLs.

urluse it for
App (port 8000)Open it in a browser and paste your token. This is the Cascade UI and API.
S3 endpoint (port 9000)Give it to the profiler. Traces upload here.

2. trace a workload

The profiler runs on Modal on an H100. Install Modal and log in once.

pip install modal
modal setup

Tracing every instruction is slow, so you trace one or a few layers, not the whole model. List the layer names first.

modal run accelsim_trace.py --model facebook/opt-125m --list-layers

Then trace and stream to your Cascade app. Use the S3 endpoint from step 1.

modal run accelsim_trace.py \
  --model facebook/opt-125m \
  --layers model.decoder.layers.10.self_attn \
  --prompt "Hello, my name is" \
  --max-tokens 4 \
  --s3-endpoint https://<your-s3-endpoint> \
  --s3-bucket cascade \
  --s3-addressing-style path

What happens

  • Each kernel's trace uploads as soon as that kernel finishes, so files arrive while tracing is still running.
  • metadata.json uploads last. It records the model, layers, prompts, the GPU it ran on, and whether the run succeeded.
  • The run name defaults to the time plus model and layers. Set your own with --run-name.

3. wait for the trace

Open the Traces screen. Your trace appears as soon as its first file lands and moves through these states.

statemeaning
uploadingFiles are still arriving. The kernel count and size grow as they do.
processingEverything has arrived. Cascade is converting the raw trace into the format the simulator reads.
readyYou can launch runs on it.
failedThe profiler reported a failure, or processing failed. The error is shown on the trace.

Open a trace to see what it came from: the model, layers, prompts, the source GPU, and every traced kernel with its grid and block size.

4. launch a run

From a ready trace, choose New run. A run is a list of GPU configs, each with a count.

  • Config is one of Accel-Sim's tested GPU models, such as SM90_H100. The trace's suggested config, the GPU it was captured on, is preselected.
  • Count is how many simulators run that config, from 1 to 64. Each one is its own sandbox.
  • Configs for a different GPU architecture are disabled. A trace from an H100 contains Hopper-only instructions, so it only runs on sm_90 configs like SM90_H100 and SM90_H200. To model another architecture, trace on that GPU.

When you launch, Cascade checkpoints its sandbox once for the run, then forks one simulator per count from that checkpoint. Every simulator starts with the same trace on disk.

5. read the results

The run screen updates live. Each simulator shows its state, when it last reported in, how many kernels it has finished, and its latest numbers.

statemeaning
pendingWaiting to be launched.
launchingIts sandbox is being forked and started.
runningSimulating and reporting in.
lostIt hasn't reported in for 60 seconds. It goes back to running if it reports again.
succeededFinished every kernel.
failedThe simulator exited with an error, or its sandbox failed to start.
cancelledYou cancelled the run.

Metrics

metricmeaning
cyclesTotal simulated GPU cycles so far (gpu_tot_sim_cycle).
IPCInstructions per cycle across the GPU (gpu_tot_ipc).
sim rateHow fast the simulator itself is running, in simulated instructions per second.
simulated timePer kernel, gpu_sim_cycle divided by the config's core clock.

Real vs. simulated

When a trace includes real kernel timings from the original GPU, the run screen lines up real against simulated time kernel by kernel and shows the error for each config. Capturing real timings in the profiler is in progress. Until it lands, this panel says so and shows simulated time only.

Downloads

  • Run results are one JSON file with the run, the trace, every simulator's per-kernel stats, and the comparison.
  • Simulator results are the same for one simulator.
  • Log is the simulator's full raw Accel-Sim output.

api

Everything in the UI is available over HTTP. Send your token as a bearer token.

curl -H "Authorization: Bearer $CASCADE_TOKEN" https://<your-app>/api/traces

curl -X POST -H "Authorization: Bearer $CASCADE_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"trace_id": "<trace-id>", "entries": [{"gpu_config": "SM90_H100", "count": 4}]}' \
  https://<your-app>/api/runs

See the API reference for every route and type, including the live event stream for a run.

bring your own simulator

Cascade starts whatever command is set in CASCADE_SIM_CMD inside each fork. Any program that follows this contract can be the simulator.

  1. Read CASCADE_SIM_ID, CASCADE_MAIN_URL, CASCADE_TOKEN, CASCADE_GPU_CONFIG and CASCADE_TRACE_DIR from the environment.
  2. Every few seconds, POST /api/sims/{id}/heartbeat with {"state": "running"}. Stop if the reply has "cancel": true.
  3. Send output as POST /api/sims/{id}/logs with {"seq": n, "lines": [...]}. Increase seq by one each time. A repeated seq is ignored, so retrying is safe.
  4. Finish with a heartbeat of "succeeded" or "failed" and your exit code.

Send Accel-Sim's stdout as is. Cascade parses the per-kernel stats out of it for you.

troubleshooting

symptomwhat to check
Trace stuck in uploadingThe profiler hasn't uploaded metadata.json yet, which it sends last. Check that the Modal run finished.
Profiler can't reach the bucketUse the S3 endpoint URL, not the app URL, with --s3-bucket cascade and --s3-addressing-style path.
A config is disabledIt's for a different GPU architecture than the trace. Trace on that GPU instead.
A simulator shows lostIts sandbox stopped reporting. It recovers on its own if it reports again. If it doesn't, open its log.
Token rejectedUse the exact CASCADE_TOKEN the app was deployed with.

limits

  • Each simulator models one GPU. Making many simulated GPUs act as one system is the next step, not something Cascade does yet.
  • A trace only runs on configs of the architecture it was captured on.
  • Traces grow with the layers, tokens and forward passes you trace. A small layer is tens of MB. Whole models with long prompts can reach hundreds of GB. The app needs about 2.2 times the uploaded size in disk.
  • Simulation is much slower than real hardware. Start with one layer and a few tokens.
