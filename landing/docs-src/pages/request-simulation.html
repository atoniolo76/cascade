A finished instruction simulation is a hardware performance profile, not a measurement of every possible request. Cascade uses that profile to estimate new prompt/output sizes and to run a discrete-event, vLLM-v1-like request scheduler. No model inference or new GPU calibration is performed by this request layer.

Outside-calibration predictions are unvalidated. The bundled OPT-125m profiles have one prefill size, 6 tokens, and decode contexts 7–37. Longer prompts, longer contexts and concurrent/chunked batches have not been validated by new GPU runs. Do not interpret a plausible latency or throughput number as measured performance or a proven accuracy bound.

Choose the right interface

  • Request simulator UI: open the sidebar entry and choose a ready trace and supported GPU config, or use the link on a finished run/sim to prefill both. Enter prompt/output tokens, request count and arrival rate; expand the advanced scheduler assumptions if needed. Results include percentile cards, sortable/paginated request metrics, step charts, calibration and provenance.
  • POST /api/scenarios: simulate explicit arrivals or a shorthand workload with continuous batching. It uses the usual API bearer authentication. Results are transient, not persisted as new inference runs.
  • POST /v1/completions or /v1/chat/completions: estimate one submitted request with the same performance profile. /v1 never batches across HTTP requests, even when calls arrive simultaneously.

The request-sizing targets are exactly SM90_H100, SM90_H200 and SM80_A100, and the chosen config must be installed in the app's GPU-config registry. Trace/config architectures must match: H100 traces can use H100/H200; native A100 traces are required for A100. Other targets, quantized models and tensor-parallel models are unsupported. This is a single-GPU, dense-model approximation, not a general vLLM emulator.

Build a profile from a finished sim

  1. Resolve the trace by exact ID or by model name (newest ready trace), then its GPU config. The shared resolver first reuses a successful sim with posted step timing; otherwise it attaches to a pending/launching/running sim, or launches a normal one-sim base run. fresh: true requests a new base run.
  2. Wait for base timing up to CASCADE_OPENAI_WAIT_S, default 3600 seconds. A timeout is 504, with the base run/sim IDs; it does not cancel the run. Failed sims or success without a step timeline return 502. The UI links matching active simulations while waiting.
  3. Combine the stored real corrected_timeline.json metadata with supplied run.json/workload.json and the stored simulated timeline. build_profile requires steady, single-request repeats with one unchunked prefill each and a common profiled prompt/output shape.
  4. Classify kernels, sum simulated durations by group, and take medians over repeats for each kind/context. Record separate prefill and decode host residuals (step wall − GPU busy), unattributed GPU busy, inter-step gaps, pre-first-step envelopes and signed post-last-step envelopes.
  5. Cache the resulting PerfProfile in process memory by sim_id, up to 128 profiles. Different request sizes reuse the base sim; scenario results themselves are not cached or saved. Only an absent/fresh base creates a normal run visible in the existing UI.

Bundled samples reuse their recorded simulations and reject fresh: true: instruction traces are not bundled. The CPU Accel-Sim execution remains in the simulator, never the profiler. Request sizing is a separate pure-Python performance model over finished timing; it does not generate or replay new-shaped SASS traces.

Kernel groups and roofline floors

Grouping is heuristic, based on kernel names and launch shape. Model dimensions supply hidden/FFN widths, layers, heads/KV heads, vocabulary and dtype byte width. A missing FFN width is assumed to be 4 × hidden; missing OPT vocabulary is assumed to be 50,272. Such fallbacks appear in the assumptions list.

GroupIdentification / approximate work
linearGEMM/GEMV, cuBLAS/CUTLASS/xmma and related matmuls. FLOPs ≈ 2 × non-embedding parameters × total query tokens; bytes include body weights and activation traffic.
attentionFlash/attention/paged attention kernels. FLOPs ≈ 4 × layers × hidden × Σ(query tokens × context); KV-read bytes scale with the sum of per-sequence contexts.
kv_writeIdentifiable reshape/cache writes, separated from attention; bytes scale with query tokens × KV bytes/token.
lm_headExplicit name, or the final linear launch when its grid is at least twice the median linear grid. FLOPs ≈ 2 × hidden × vocabulary × sampling sequences, plus projection-weight bytes.
samplerSampling/top-k/argmax/softmax-like work, proportional to vocabulary and sampling sequences, not all prompt tokens.
elementwiseRemaining operations, including reductions and layer norms; approximate memory traffic scales with query tokens × hidden × layers.

For a batch, the model receives per-sequence query-token and context vectors, not merely a total token count. LM-head/sampler work counts only sequences that sample on this step: ordinary decode or a completed prefill. Intermediate prefill chunks omit those groups.

```text roofline(group, shape) = max(FLOPs / (0.7 × peak compute), bytes / (0.8 × peak bandwidth)) predicted group time = max(baseline group floor, anchored roofline time) step wall = assumed host(kind) + sum(predicted group times) + residual GPU busy ```

The roofline is anchored downward if needed so its calibrated-shape value cannot exceed the corresponding simulated group floor. That anchoring is not a fitted scaling law. Decode floors interpolate between available baseline contexts and clamp at endpoints outside their range; the prefill floor comes from its single recorded size. Only the roofline term grows beyond the range. Linear activations assume 8 memory passes and elementwise work 16 passes; the dense FFN is ungated with two projections, and biases/norm parameters are omitted.

Matching calibrated group times reproduce their simulated floors exactly. Full request estimates use median components rather than replaying each repeat, so they need not equal the base timeline's mean E2E exactly. Baseline floors and retained eager host time can dominate: a nearly flat predicted ITL is not evidence that long contexts are free.

Scheduler semantics

  1. Arrivals and idle time. Arrivals enter a waiting queue in stable order. If no request is runnable, advance to the next arrival rather than consuming fake GPU steps.
  2. Running first, decode first. Schedule running decode requests (one query token each) before partial prefills. Respect the sequence and batched-token budgets; a mixed step uses prefill-kind host/gap assumptions if it contains any prefill work.
  3. FCFS admission and chunked prefill. Admit waiting requests first-come, first-served as budgets/KV space permit. With chunking enabled, split prompts across steps to fit the token budget. Without it, a prompt larger than the budget is rejected.
  4. KV blocks and recompute preemption. Allocate blocks as context crosses block boundaries. Under memory pressure, preempt the most recently admitted running request, free its blocks and place it at the front of waiting. Recompute its prompt plus already generated prefix; retain its emitted tokens and do not emit them twice. It cannot be readmitted in the same step.
  5. Time and emissions. Use the batch GPU estimate plus kind-specific host time, profiled inter-step gaps and one pre-step envelope per busy period. Tokens emit at actual step ends. Completion retains the signed post-step envelope; completed requests free their blocks.

TTFT and E2E start at arrival; queue time ends at first GPU-step start. Per-request ITL is computed from successive token timestamps. Aggregate p50 ITL pools those intervals, percentiles use linear interpolation, and output throughput divides total emitted tokens by first-arrival-to-last-completion time. A single request at time zero agrees with simulate_request within 1e-6 relative in the consistency tests. Zero output still performs prefill, with null TTFT/ITL; one output has no ITL interval.

Resolved vLLM scheduler defaults and KV-block capacity were not captured in the sample traces. These settings are scheduler assumptions, not a claim to reproduce the exact vLLM deployment configuration. Memory utilization is distinct from the roofline's bandwidth-efficiency fraction, even though both can be 0.8.
```text KV bytes/token = 2 × layers × KV heads × head dimension × dtype bytes weight bytes = (dense body parameters + hidden × vocabulary) × dtype bytes KV blocks = floor((GPU memory bytes × utilization − weight bytes − 1 GiB) / (block_size × KV bytes/token)) ```

The embedding/projection weights are assumed tied. The fixed activation reserve is 1 GiB = 1,073,741,824 bytes; fragmentation is ignored. An explicit num_kv_blocks overrides the estimate and can intentionally model a smaller budget. Impossible isolation capacity, or an unchunked recompute prefix exceeding the token budget, returns an error rather than looping indefinitely.

Scenario API example

This example reuses the H100 bundled sample and submits eight simultaneous requests, each with 512 prompt tokens and 128 output tokens. It performs no new Accel-Sim execution.

```bash curl "$CASCADE_URL/api/scenarios" \ -H "Authorization: Bearer $CASCADE_TOKEN" \ -H "Content-Type: application/json" \ -d '{ "trace_id": "sample__facebook_opt-125m__h100-e2e", "gpu_config": "SM90_H100", "num_requests": 8, "prompt_tokens": 512, "output_tokens": 128, "arrival_rate_rps": 0, "scheduler": {"max_num_seqs": 256, "max_num_batched_tokens": 8192} }' ```

Rounded response excerpt from the request-simulator example; omitted fields include per-request metrics, per-step records, resolved scheduler and the full assumption list:

```json { "trace_id": "sample__facebook_opt-125m__h100-e2e", "gpu_config": "SM90_H100", "run_id": "run-sample-opt125m-h100-e2e", "sim_id": "sim-sample-opt125m-h100-e2e", "cached": true, "aggregate": { "p50_ttft_ms": 9.799, "p99_ttft_ms": 9.799, "p50_itl_ms": 8.125, "p50_e2e_ms": 1041.514, "p99_e2e_ms": 1041.514, "throughput_output_tokens_s": 983.184 }, "steps_total": 128, "steps_returned": 128, "steps_downsampled": false, "provenance_counts": { "measured": 0, "interpolated": 0, "extrapolated:roofline": 128, "assumed-host": 128 }, "calibration_range": {"prefill_tokens": [6, 6], "decode_context": [7, 37]} } ```

Provide exactly one selector, trace_id or model. Shorthand requires num_requests, prompt_tokens and output_tokens. Null/zero/omitted arrival rate means all arrive at zero; a positive rate produces deterministic arrival i / arrival_rate_rps, not a Poisson process. For explicit requests, replace the shorthand fields with:

```json { "trace_id": "sample__facebook_opt-125m__h100-e2e", "requests": [ {"id": "a", "arrival_s": 0, "prompt_tokens": 512, "output_tokens": 128}, {"id": "b", "arrival_s": 0.5, "prompt_tokens": 512, "output_tokens": 128} ] } ```

Do not mix explicit requests with shorthand fields. Omitted IDs become request-<index> and must remain unique. Prompts must be positive integers, outputs nonnegative integers, and prompt plus output must fit the supplied model limit (2048 if absent). Invalid bodies return 422. Service safety limits are 4096 requests, 1,000,000 total prompt/output tokens, 100,000 executed steps, and finite arrivals within 0–1e9 seconds. These are not vLLM limits.

Above 5000 steps, the response uniformly downsamples records while retaining first/last and original step_index; steps_total, steps_returned, steps_downsampled and steps_sampling disclose it. Aggregate/request metrics and provenance counts always use all executed steps. The UI may further subsample chart points; it does not recalculate the metrics from the plotted subset.

OpenAI-compatible single-request example

```bash curl "$CASCADE_URL/v1/completions" \ -H "Authorization: Bearer $CASCADE_TOKEN" \ -H "Content-Type: application/json" \ -d '{ "model": "sample__facebook_opt-125m__h100-e2e", "gpu_config": "SM90_H100", "prompt": "Hello, my name is", "max_tokens": 32, "seed": 42 }' ```

With the OPT tokenizer reporting six prompt tokens, the requested-shape model predicts 8.946 ms TTFT, 8.125 ms mean ITL and 260.593 ms E2E (rounded). These request-layer estimates use median profile components; they are not the base replay's per-repeat means. Check usage.prompt_tokens and cascade.prompt_tokens_source before comparing with this six-token example.

  • cascade.timing contains requested-size TTFT, mean/p50 ITL, E2E, token counts, calibration, assumptions and provenance. cascade.profiled separately retains base-workload real/simulated metrics and its comparison summary. profile_match remains a prompt/output match flag, not proof of accuracy.
  • Output length is max_tokens for completions; chat accepts max_tokens or max_completion_tokens (conflicting values are rejected). The default is the trace workload's max_tokens. Timing uses that resolved count, not the base workload's output count.
  • Prompt usage and timing use the same tokenizer count. Chat applies a usable cached chat template, otherwise joins message contents with newlines. If the tokenizer is unavailable, the deterministic estimate is max(1, ceil(UTF-8 bytes / 4)), flagged estimated:utf8-bytes/4; the prompt above then estimates five tokens, not six. Other sources are tokenizer, tokenizer:chat_template and tokenizer:joined.
  • Response text is uniformly sampled non-special vocabulary IDs, seedable with seed; unavailable tokenizers use flagged tok<i> placeholders. This is not semantic text generation. Completion usage counts sampled IDs, which decoded text may re-tokenize differently.
  • With stream: true, final chunks carry the same timing/profiled structure after progress comments and content deltas; chunks are not paced like actual inference. Concurrent /v1 calls can share a base sim but never share a scheduler batch.
