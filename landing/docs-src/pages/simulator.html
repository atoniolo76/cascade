Cascade runs whatever command is in `CASCADE_SIM_CMD` inside each sim. The app ships one, `cascade worker`, which runs Accel-Sim. Any other program that follows this contract can be the simulator: a patched build, or something else entirely.

The contract

  1. Read your identity from the environment.
    variablevalue
    `CASCADE_SIM_ID`This sim's id, such as `sim-6b4c91e71437`.
    `CASCADE_MAIN_URL`The app's URL, from `CASCADE_PUBLIC_URL`.
    `CASCADE_TOKEN`The bearer token for every request.
    `CASCADE_GPU_CONFIG`The config to simulate, such as `SM90_H100`.
    `CASCADE_TRACE_DIR`The trace's directory. The processed trace is at `$CASCADE_TRACE_DIR/traces/kernelslist.g`.
    `CASCADE_ACCELSIM_DIR`The app's `CASCADE_ACCELSIM_DIR`, where Accel-Sim and its configs live.
  2. Send `POST /api/sims/{id}/heartbeat` with `{"state": "running"}` right away, and again every few seconds. If the reply has `"cancel": true`, stop and exit.
  3. Send your output as `POST /api/sims/{id}/logs` with `{"seq": n, "lines": [...]}`, counting `seq` up from 0. Send Accel-Sim's stdout as it is. The app parses the per-kernel stats out of it.
  4. Finish with one heartbeat of `succeeded` or `failed`, with your `exit_code`, and an `error` if you failed.

[Simulator endpoints](api-simulator.html) has the full request and response for both calls.

Retries are safe

Both calls are safe to repeat, so retry any `5xx` or network error with backoff. The app ignores a log chunk whose `seq` it already has, and a heartbeat that repeats the current state only refreshes the heartbeat time. Don't retry a `4xx`. It means the token or the body is wrong, or the sim doesn't exist.

Keep heartbeats going while you wait on retries. After 60 seconds of silence the sim shows as `lost`, and after 600 seconds it fails and the app stops its sandbox.

The built-in worker

`cascade worker` follows this contract for Accel-Sim. To use it, deploy with `--sim-cmd "/app/.venv/bin/cascade worker"`.

  • It runs `$CASCADE_ACCELSIM_DIR/gpu-simulator/bin/release/accel-sim.out -trace $CASCADE_TRACE_DIR/traces/kernelslist.g` with the sim's `gpgpusim.config` and `trace.config`. It runs in a fresh directory, `$TMPDIR/cascade-worker//`, with a copy of every file in both config directories, because some configs name their aux files by relative path.
  • It keeps the full log in that directory as `accelsim.log`.
  • If the binary, a config or `kernelslist.g` is missing, it sends a `failed` heartbeat with exit code 2 and an error that names the missing path.
  • It sends a chunk every 200 lines or 0.5 seconds, a heartbeat every 5 seconds, and every chunk before its final heartbeat.
  • `cascade worker --replay ` replays a recorded Accel-Sim log instead of running Accel-Sim. `--delay` sets the pause every 200 lines, 0.05 seconds by default. This is the stand-in simulator.

Step timing

A trace can carry two more files next to `metadata.json`. When both are there, the trace's `has_step_timeline` is true. The app checks on every scan, so they can arrive after the trace is ready.

  • `corrected_timeline.json`, the profiler's per-step timeline of the real run.
  • `kernel_mapping.json`, a list of `{"uid", "name", "repeat", "step", "seq"}`. `uid` and `name` name a kernel in the sim's log. `repeat`, `step` and `seq` name the kernel in the corrected timeline that the sim's time replaces.

After a sim succeeds on such a trace, `cascade worker` runs the step-timing model in `cascade/sim/` on its own log. It imports each mapped kernel's cycles with the config's core clock, rebuilds every step with `cascade simulate`'s defaults, and compares the result with the corrected timeline using `cascade compare`. Then it sends both results to [Send step timing](api-simulator.html#post-step-timeline), before its final heartbeat. If either file is missing, it writes one log line and skips this. If the model fails, for example because the mapping names a kernel the log doesn't have, the sim still succeeds, nothing is sent, and the error goes to the log.

A complete client

To run a simulator other than Accel-Sim, write your own client. This one runs any command, forwards its stdout as log chunks, sends a heartbeat every 5 seconds, stops the command if the run is cancelled, and reports the exit code. It uses only the Python standard library.

{{snippet cascade_sim.py}}

Put it in your simulator image and point `CASCADE_SIM_CMD` at it, followed by your command. On Sail, the app runs the command through a shell inside the fork, so `$VARIABLES` such as `$CASCADE_GPU_CONFIG` expand there. Quote them with single quotes so your own shell leaves them alone. The local launcher splits the command into arguments with `shlex` and runs it without a shell, so they don't expand locally.

What the image needs

The app is layered on top of your image with the Dockerfile's `BASE_IMAGE` argument, so the app and every sim run the same image. It needs these things.

The trace post-processor`CASCADE_POSTPROCESS_CMD`, by default `$CASCADE_ACCELSIM_DIR/util/tracer_nvbit/tracer_tool/traces-processing/post-traces-processing`. The app runs it on the main sandbox, not in sims.
Accel-Sim`$CASCADE_ACCELSIM_DIR/gpu-simulator/bin/release/accel-sim.out`, and each config's `trace.config` under `$CASCADE_ACCELSIM_DIR/gpu-simulator/configs/tested-cfgs/`. `cascade worker` runs it.

Pin the simulator to the version the profiler traced with. The profiler at `b348d7d` builds the tracer from Accel-Sim commit `7ba54ded`. The app's notes name Accel-Sim tag `v2.0.1` for the simulator.

Where output goes

Anything your command prints to stdout or stderr is also saved to `$CASCADE_DATA_DIR/work/sims/.out` on the sim's disk. Only what you send to `/logs` reaches the app, and only that gets parsed.
