Getting started

Introduction

Cascade takes a trace of an ML workload captured on one real GPU and simulates it on other GPU configs, many copies at once. You trace once, then ask how the same kernels run on an H100, an H200 or a dozen replicas of each.

Worked example: OPT-125m on an H100#

A full 32-token request: 254.45 ms real, 262.14 ms simulated — +3.02%. This is facebook/opt-125m on a Modal H100 80GB HBM3, with the six-token prompt Hello, my name is, vLLM 0.21.0 in eager mode (no CUDA graphs / torch.compile). Means cover repeats 1–3; repeat 0 is warm-up.

Where the error comes from#

The profiler measures unprofiled request/step timing and Nsight kernel timing separately. NVBit traces four steps (prefill and decode at contexts ≈ 8, 16, 32); Accel-Sim simulates 31 distinct kernels, then propagates durations to 17,088 steady kernel launches. Replay swaps in simulated kernel durations while retaining measured host residuals, gaps and unmatched GPU activity.

Kernel means compare the 712 aligned traced occurrences, not full-request-weighted decodes; group roles are inferred from kernel names. Interpretation: a ~3 µs (~6,000-cycle) per-kernel floor makes tiny kernels 1.5–2.3× too slow. With 178 kernels per step, small elementwise, layer norm, KV-write and split-K kernels account for about 200 µs of the ~240 µs step over-prediction (derived). Calibrating that floor is the main accuracy opportunity.

Small request error is not small GPU error. Decode GPU busy is 575.6 µs real versus 817.0 µs simulated (+41.9%, about +42%). In eager mode, about 93% of step wall time is the retained host residual (a derived residual, not independently measured CPU time). That dilutes GPU error to about +3% e2e; CUDA graphs could move request error toward ~42% unless the floor is calibrated.

H100 traces run on H100/H200 (sm_90); older architectures are rejected for mismatch. H200 differs here only in memory-controller count (40 → 48), yielding +0.02 ms per request. Inference: this small workload does not separate the configs; the simplified H200 model is not a validated physical H200.

Coverage is 100%, not proof of accuracy: dedup verification found up to 39.7% cycle disagreement in one small-kernel group. Attention and KV-write cycles are reused across short contexts, so this is not a context-scaling result.

Numbers follow the OPT-125m results draft and the committed hardware sweep. See the full OPT-125m analysis for evidence, pipeline costs, per-kernel detail and caveats.

How it fits together#

Cascade has three parts. Each part runs in a different place, and they talk over S3 and plain HTTP.

  • Profiler. Runs your workload, such as a vLLM model, on a Modal H100 under Accel-Sim's NVBit tracer. It uploads each kernel's trace to the Cascade app while tracing is still running.
  • Cascade app. One Sail sandbox that receives traces over S3, gets them ready to simulate, launches runs, and shows everything in a web UI and an HTTP API.
  • Simulators. Each simulator is a fork of the app's sandbox, so it starts with the trace already on disk. It runs Accel-Sim against one GPU config and reports progress back to the app.
